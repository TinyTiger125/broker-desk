# 账号与角色 E2E 验收

本清单验证真实 Clerk 身份、数据库成员关系和前台权限是否一致。自动门禁只能验证数据库授权与数据完整性；以下步骤必须用三名真实测试用户完成。

## 前置条件

- 使用独立的 Clerk 测试身份：平台管理员、租户管理员、普通经纪人。
- 三个身份均已完成邮箱验证，并且只加入指定测试工作区。
- 记录测试工作区、三名用户的 Clerk subject、执行日期和浏览器版本；不要记录密码或 API 密钥。

## 平台管理员

1. 登录后可进入账户生命周期、官方模板管理和工作区成员管理。
2. 可创建测试工作区、设置席位并发送邀请；普通用户不能自行创建账号或获得工作区访问权。
3. 停用一个已激活成员后，该成员刷新页面即失去工作区访问权；恢复成员后可重新进入。
4. 可发布官方模板版本；在一个租户中安装模板后，修改官方版本不会直接改写该租户的本地框体。

## 租户管理员

1. 登录后只能看到被分配的工作区和数据，不能进入平台账户生命周期或官方模板编辑。
2. 可管理本工作区成员、安装官方模板、维护本工作区的必填规则与本地模板副本。
3. 尝试通过地址栏访问另一个工作区、平台管理页面或另一个租户的附件/输出 API，必须被拒绝而非展示空白数据。

## 普通经纪人

1. 登录后只能看到被分配的工作区；没有成员、账户生命周期和官方模板编辑入口。
2. 可新建/补充案件、上传材料、确认资料字段、预览允许的输出内容。
3. 将 cookie 中的工作区标识改为其他有效工作区后，必须被拒绝。
4. 被停用或移出工作区后，刷新、重新登录和直接打开旧链接均不能读取原数据。

## Clerk 生命周期

1. 在 Clerk 创建或更新测试用户后，Webhook 日志为成功，数据库本地用户保存对应不可变 subject。
2. 受邀成员首次登录后，成员状态从 `invited` 变为 `active`，且只激活其已有邀请。
3. 在 Clerk 删除测试用户后，数据库清除其 external subject，并将其工作区成员关系置为 `suspended`。

## 通过条件

- 三种身份均完成上面的正向与负向场景。
- 没有 500 错误、权限越界、跨工作区数据泄露或非产品化错误页面。
- 自动门禁 `npm run test:tenant-auth-lifecycle-state` 和 `npm run test:postgres-rls` 均通过。

未执行本清单时，不得把角色系统标记为“真实 E2E 已验收”。

## 2. 产品定位

Broker Desk 的核心定位：

```text
面向日本房地产经纪的资料机器人 / 房产资料生产中枢。
```

它不是单纯的资料库，也不是单纯表单工具。它要帮助经纪人完成：

1. 录入资料：上传 Excel、PDF、图片、在留卡、申请资料等。
2. 读取资料：系统尽可能读取并抽取字段。
3. 归集资料：把资料归到案件、主体、物件。
4. 核对资料：让经纪人快速确认、修正、补全。
5. 输出文件：生成保证公司申请书，未来扩展为更多官方/行业文书。
6. 形成可被模型使用的结构化房产知识库。

长期 AI 原生定位：

- AI 不应该只是一个菜单项，而应该常驻在系统流程中。
- 系统应像一个“房产中介的龙虾机器人”：它在后台读资料、找差异、提醒缺项、协助填写、准备输出。
- 但当前阶段不能为了“AI 感”牺牲确定性。AI 结果必须进入可核对、可修正、可追溯的业务链路。

## 3. 已固定的产品原则

### 3.1 流程要线性，不重复

首页/工作台只承担“从哪里开始”的选择，不应该塞太多列表和后台细节。

录入资料、整理信息、输出文件是三条主流程链：

```text
工作台
  ├─ 录入资料
  ├─ 整理信息
  └─ 输出文件
```

同一个操作不要在多个页面重复出现。例如：

- 如果“整理信息”已经在导航里存在，录入页不需要再放“去整理信息”按钮。
- 如果案件列表已经展示，旁边不需要再放“请先选择目标案件”按钮。
- 如果列表项可以双击进入编辑页，不要再堆一个“继续整理”按钮。

### 3.2 产品语言必须对外

删除或改写这类内部语言：

- “这里只显示……”
- “避免把联系人、物件和案件混在一起”
- “读取后只会把核对画面中采用的项目写入……”
- “当前分类没有待填写项目”
- “按系统统计……”

必要说明要改成客户向、动作向，例如：

- “选择要整理的资料类型”
- “选择案件后生成申请书”
- “上传在留卡、驾照或本人确认资料”
- “把 Excel 文件拖到这里，或点击选择”

### 3.3 人名、地址、原始属性不硬翻译

中文界面可以翻译系统词，但不要把日本地址、日文姓名、公司名硬翻成中文。  
日语实际环境中的 UI 字典后续由朋友审校。

### 3.4 页面要干净，信息按层级展开

第一屏只放当前决策所需的信息。  
次级信息通过点击、双击、折叠、详情页进入，不在首页铺满。

### 3.5 案件 / 主体 / 物件必须统一编辑体验

之前三个对象的编辑页风格不一致，这是用户明确无法接受的问题。  
未来必须统一为同一套编辑框架：

```text
顶部：对象摘要与总体进度
左侧：章节/分类导航，必须可折叠、不能无限长
中间：当前章节字段列表
右侧：当前字段的核对与修改面板，核心操作始终可见
```

## 4. 当前页面拓扑与约定

### 4.1 工作台

工作台是“现在要做哪一步”的入口。  

保留三个主要大入口：

- 录入资料
- 补齐信息
- 输出文件

之前首页下方待办列表过重，已改为“资料助手”/收纳式轻入口方向。后续仍要继续控制首页信息量。

### 4.2 录入资料

目标：让经纪人把文件放进系统。

已确定方向：

- 页面只保留新开案件、新建主体、新建物件入口，以及两个大上传区。
- 上传区分左右两块：
  - 本人资料：PDF / 图片
  - 申请资料 / 台账：Excel / `.xlsx`
- 上传区应该支持点击选择和拖拽。
- 不要再显示“多人 / 多文件 / 处理方式”等复杂选项。
- 不要放“去整理信息”按钮，避免流程重复。

### 4.3 整理信息首页

用户和朋友最新会议后确认：

整理信息第一页只保留四个对象入口：

- 案件
- 主体
- 物件
- 待归属资料

不再显示：

- 搜索框
- 下方列表
- 当前对象侧栏
- 筛选栏

点击四个入口后进入第二层列表页。

### 4.4 整理信息第二层列表

第二层列表页应保持干净：

- 只保留搜索框和下方列表。
- 列表按最近使用时间排序。
- 不显示左侧筛选栏。
- 不显示右侧“当前对象”信息栏。
- 列表分页只作用于下方列表，不影响顶部对象入口或页面其他区域。
- 双击列表项进入对应编辑页。
- 不再放“继续整理”按钮。
- 顶部四大对象切换时不得跳到页面顶部或发生乱蹦。

当前仍存在问题：

- 顶部分类切换后自然滚动位置不一致。
- 下方列表可能过长，分页与滚动稳定性仍需继续验证。

### 4.5 案件 / 主体 / 物件编辑页

这是当前最重要的体验问题之一。  

用户和朋友的关键判断：

- 填资料本身也是核对过程，不能只显示未填写项。
- 但传统密集表单太痛苦，不能回到满屏输入框。
- 最佳方向是“章节列表 + 字段列表 + 当前字段核对面板”。

目标结构：

```text
对象编辑页
  ├─ 顶部对象摘要：申请人 / 物件 / 保证公司 / 负责人 / 待核对 / 已确认 / 总进度
  ├─ 左侧章节导航：按业务章节分组，可折叠，不能无限长
  ├─ 中间字段列表：显示状态、项目、当前值、动作
  └─ 右侧核对面板：显示资料内容、确认内容、确认并保存
```

状态必须简化：

- 未填写
- 待核对
- 已确认

避免过多状态词造成认知负担。

已发现问题：

- 当前版本虽然有表格雏形，但还没有完全符合设计稿。
- 左侧章节列表过长时造成右侧大量留白。
- 核心修改/确认动作不应被压到页面最底部，必须保持可见。
- 顶部摘要卡图标有裁切/显示不全问题。
- “保存并确认”应改为“确认并保存”。
- “资料来源 / 查看来源”板块用户认为大概率没人看，可删除或极度弱化。

### 4.6 输出文件

当前阶段只保留有实际价值的保证公司申请书。

已确定方向：

- 除保证公司申请书之外，之前预设的“物件概要书 / 购买提案书 / 费用估算明细书 / 资金计划书”等自动生成文书都不能以敷衍版本继续展示。
- 未来新增文书必须先调查官方或行业标准版本，再接入。
- 输出页应先选择文书类型，再选择案件，再选择保证公司模板，随后展示预览。
- 预览必须显示真实填入数据，不应只是空模板。
- 预览区域不需要 PDF 页缩略导航，只显示预览内容。
- 预览太小时必须支持全屏放大。

当前仍存在关键问题：

- 某些保证公司模板预览显示为空表，用户认为没有预览意义。
- 选择保证公司后页面可能跳回顶部，必须保持当前区域。
- 选择保证公司后应该立即刷新预览，让用户有反馈。
- “请先选择目标案件”控件在下方已有案件列表时没有意义，应删除。

### 4.7 设置

设置区域只放设置和说明，不放业务功能。

保留方向：

- 团队成员 / 权限
- 必填项目
- 文书抬头 / 文书格式

已删除/需删除方向：

- “智能填写”作为单独设置入口意义不清，应取消入口。
- AI 经验不应丢失，应作为模型上下文链和后台学习能力保留在文档与数据结构中。

必填项目设置：

- 按租户/账号差异配置。
- 有默认版本，但每个经纪公司可调整。
- 必填项优先出现在未填写顶端，选填项后置。
- 页面不应是长表格，应改为类似思维导图的强分类 + 分支点选。

## 5. AI 能力定位

当前产品还偏“强功能 / 强代码”，用户认为 AI 介入感不足。  
后续不能把 AI 做成一个可有可无的菜单，而要做成贯穿流程的能力。

AI 当前和未来应承担：

1. 读文件：OCR、Excel/PDF/图片解析。
2. 建事实：把读取内容落到案件、主体、物件字段。
3. 找差异：发现同一字段在不同资料中的不一致。
4. 找缺项：告诉用户下一步最值得处理什么。
5. 解释来源：在需要时知道字段来自哪个资料，但不必默认占据页面空间。
6. 学习修正：用户每次确认/修正都成为后续模型经验。
7. 生成输出：把已确认事实写入保证公司申请书和未来文书。
8. 未来扩展：客户触达 Agent、空间资料采集/3D 扫描、房源知识补全。

3D / 空间扫描讨论结论：

- 不计划自研 3D 建模底层。
- 3D 的价值不在“好看”，而在“空间资料采集和房源知识补全”。
- 若接入，应服务于房源资料编纂：识别房间、设施、空间关系、图片素材、卖点、隐私检查。
- 是否值得做取决于它能否减少经纪人的真实工作时间或显著提高资料完整度。

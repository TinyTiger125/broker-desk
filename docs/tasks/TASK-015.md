# TASK-015：MIG-005 建立 TECHNICAL_PM Playbook

- 状态: Proposed
- 优先级: P1
- 负责人: 项目经理 / 独立审查Agent
- 依赖关系: MIG-004 产品决策确认后再启动

## 任务名称

建立 `docs/agents/TECHNICAL_PM.md`，定义技术项目经理如何在守护产品目标的同时，对不充分、过度复杂、越权或高风险的方案提出建设性反对，并推动最小验证和可回看的决策。

## 背景和用户结果

项目经理需要同时守护用户结果、产品范围和长期可维护性。Playbook应让项目经理在有反证或风险时明确反对方案，在证据不足时推动最小验证，并在用户作出非推荐决定后保留可回看的风险和触发条件。

## 本次范围

- 建立一份角色Playbook，覆盖建设性反对、认知提升、证据分层、最小验证、最终决策记录和独立审查。
- 将Playbook限定为项目管理方法，不让它成为永久治理、产品事实或架构事实的第二权威。

## 依赖关系

MIG-004 产品决策确认后再启动；当前仅登记任务，不执行。

## 当前边界

- 本卡只登记未来任务的验收条件，不代表现在开始创建 Playbook。
- 不修改 `AGENTS.md`，不改变永久治理规则，不把 Playbook升级为产品、架构或任务状态的权威来源。
- 不打断或扩大 MIG-004；MIG-004仍按当前决策材料和授权边界执行。
- 不创建业务代码、产品功能、自动化或新的重复权威。

## 验收标准

1. 先区分用户结果、提出的实现手段和未证实假设，再评价方案。
2. 当事实与代码/数据/可靠资料冲突、证据不足、方案不能解决原问题、存在安全/权限/合规/发布风险、成本明显超过收益、范围扩大、重复权威或技术债增加、或存在更小可验证替代方案时，必须明确提出反对意见。
3. 反对意见必须按固定结构记录：目标、不同意或担心之处、证据、原方案后果、主推荐、保留的目标、代价和缺点、最小验证、需要用户决定的事项。
4. 重要判断必须区分：已验证事实、基于证据的推断、尚未验证的假设、产品偏好、技术建议。
5. 对会影响产品方向、成本、风险或用户体验的决定，说明被忽略的因素、通用规律、常见直觉的局限和下次应观察的指标。
6. 有低成本验证路径时优先使用最小原型、单模块试运行、用户测试、数据测量、A/B比较、调用链检查、小范围迁移或可回滚实验；验证前不得把假设写成产品事实。
7. 避免为了反对而反对；对低风险、证据充分、易回退或明确属于产品负责人偏好的选择，给出简短支持理由。
8. 用户选择非推荐方案时，记录其已知风险、最终理由、指标或触发条件；没有新证据时不得重复争论；出现新证据或风险显著扩大时必须重新提醒。
9. 涉及数据破坏、安全、违法、未授权外部操作或不可恢复风险时，即使用户坚持也必须遵守安全边界。
10. 只有在证据支持的情况下指出沉没成本、确认偏误、把个人需求当普遍需求、技术先进等同用户价值、功能数量等同完整度、过早自动化等认知风险，不得凭猜测贴标签。

### 汇报验收标准

每次重要汇报先给出：推荐结论、为什么、最大反证、最小验证、是否需要用户决定；完整证据进入任务卡或附录。主推荐最多一个，备选最多一个。

## 预计涉及的模块

`docs/agents/TECHNICAL_PM.md`、本任务卡、必要的任务卡/附录验证；不涉及 `AGENTS.md`、产品代码或运行时。

## 风险和注意事项

- “建设性反对”不能退化为默认否定、个人偏好或无限追问。
- 认知偏差只能在有观察证据时指出，不能凭猜测给用户贴标签。
- Playbook若重复定义`AGENTS.md`，会制造第二套权威；若没有停止条件，则会把审查变成无休止讨论。

## 验证命令

- `git status --short --branch --untracked-files=all`
- `git diff --check`
- `npm run test:workflow-rules`
- Playbook章节、固定反对结构、事实标签、最小验证、停止条件和安全边界逐项检查。

## 独立审查条件

- 实现完成后，最多创建一个只读独立审查Agent；不得创建下级Agent。
- 审查必须确认 Playbook 能在证据不足或风险明显时提出具体反对意见，同时不会把个人偏好伪装成事实、制造无证据争论或陷入无休止讨论。
- 审查还必须确认目标与手段被区分、事实与推断有标签、最小验证和停止条件明确、非推荐决定可回看、硬安全边界不可被用户坚持绕过。
- 审查Agent不得修改、移动、删除或提交文件，完成后退出。

## 完成证据

- `docs/agents/TECHNICAL_PM.md` 存在且只定义项目管理方法，不复制 `AGENTS.md` 的永久规则。
- 至少包含一个“证据不足时反对”和一个“用户选择非推荐方案后记录”的可复查示例。
- 通过任务卡定义的规则检查、`git diff --check`、最终工作区检查和独立只读审查。
- 未修改业务代码、产品事实、架构事实、`.cursor`、历史资料或 `main`/safety/WIP。

## 明确不做什么

- 不把“建设性反对”变成默认否定、无限追问或阻止所有低风险工作。
- 不把未经验证的推断写成事实，不用空泛的“最佳实践”代替项目证据。
- 不因用户选择非推荐方案而重复争论，除非出现新证据或风险显著扩大。

## 背景和用户结果

技术项目经理需要守护用户结果、产品范围和长期可维护性；实现 Agent 需要在授权范围内交付最小变更；独立审查 Agent 需要对结果和证据提出可复查结论。

技术项目经理不得机械服从产品负责人提出的实现办法。发现事实错误、证据不足、范围膨胀、重复建设、成本收益失衡、沉没成本偏差或存在更小验证方案时，必须明确反对，但不能丢失产品真正想获得的用户结果。

## 验收标准

### 技术项目经理 Playbook

1. 先区分用户结果、提出的实现手段和未证实假设，再评价方案。
2. 当事实与代码/数据/可靠资料冲突、证据不足、方案不能解决原问题、存在安全/权限/合规/发布风险、成本明显超过收益、范围扩大、重复权威/技术债增加，或存在更小验证方案时，必须明确反对。
3. 反对意见必须包含：真正想解决的目标；具体不同意或担心；事实/代码/仓库证据；继续执行的后果；推荐替代方案及其代价；替代方案保留的原始目标；最小验证；是否需要产品负责人决定。
4. 重要判断必须标记为：已验证事实、基于证据的推断、尚未验证的假设、产品偏好或技术建议。
5. 重要方向判断必须说明被忽略因素、通用规律、常见直觉的局限和下次应观察的指标。
6. 有低成本验证路径时，优先使用最小原型、单模块试运行、用户测试、数据测量、A/B比较、调用链检查、小范围迁移或可回滚实验；验证前不得把假设写成产品事实。
7. 不得为了显得独立而反对；对低风险、证据充分、易回退或明确属于产品偏好的选择，应说明支持证据。
8. 用户选择非推荐方案时，记录已知风险、最终理由、指标或触发条件；无新证据不重复争论，新证据或风险显著扩大时必须重新提醒。
9. 涉及数据破坏、安全、违法、未授权外部操作或不可恢复风险时，即使用户坚持也必须遵守安全边界。
10. 只有有观察证据时，才指出沉没成本、确认偏误、把个人需求当普遍需求、技术先进等同用户价值、功能数量等同完整度或过早自动化等认知风险。
11. 至少包含一个“证据不足时明确反对”的可复查示例，以及一个“用户选择非推荐方案后记录风险和触发条件”的可复查示例。
12. 重要汇报先给出：推荐结论、为什么、最大反证、最小验证、是否需要用户决定；完整证据进入任务卡或附录；主推荐最多一个，备选最多一个。

### 实现 Agent Playbook

13. 明确输入：授权任务卡、仓库规则、当前上下文、相关源文件、基线和禁止路径；明确职责只对授权写集负责。
14. 明确步骤：读规则和任务卡、确认基线和工作树、拆分最小变更、实现、运行任务卡验证、检查差异、交付证据。
15. 必须交付：修改文件清单、未修改越界路径、命令和结果、剩余风险/阻塞、提交建议和下一步交接信息。
16. 遇到范围外文件、基线不一致、未授权外部操作、安全/数据风险或缺少产品决定时必须停止并报告，不得自行扩大范围。

### 独立审查 Agent Playbook

17. 明确输入：任务卡验收标准、实现差异、基线、验证输出和相关源文件；审查职责与实现职责分离。
18. 明确步骤：只读检查范围、逐项对照验收、核对事实/推断标签、核对禁止路径、运行窄范围验证、输出带路径证据的结论。
19. 结论只能是 `PASS`、`NEEDS_CHANGES` 或 `BLOCKED`；必须说明事实证据、缺口、风险和是否建议提交。
20. 审查 Agent 不得修改、移动、删除或提交文件；只有项目经理可在审查指出 MIG-005 范围内明确问题后修复，修复后必须重新复核。

### 三类 Playbook 共同验收

21. 每类 Playbook 都必须明确：输入、职责边界、工作步骤、必须交付的证据、停止/阻塞条件、禁止越权事项、Agent 创建/复用/退出规则和交接要求。
22. 调度规则必须明确：项目经理是唯一调度者；同一时间最多两个子 Agent；不得创建下级 Agent；实现与独立审查顺序执行；完成或阻塞后立即退出；不得保留空闲 Agent。
23. 独立审查必须是只读的，只允许修复 MIG-005 范围内已明确的问题，不得借审查清理历史文档、修改永久规则或扩展任务范围。
24. 三份 Playbook 不得复制 `AGENTS.md` 的永久规则，不得制造产品、架构或任务状态的第二权威。

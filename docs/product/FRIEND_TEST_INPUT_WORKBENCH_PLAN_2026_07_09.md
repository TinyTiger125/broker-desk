# 2026-07-09 朋友测试反馈与输入工作台改进计划

## 测试结论

测试反馈验证了两个事实：

1. 自动生成保证公司申请书有明确价值。用户认为做好后会替代 Excel / 手填 PDF。
2. 当前最大阻力不在输出能力，而在输入和整理体验：不知道从哪里开始、看不到整体完成度、录入时反馈弱、输出路径不明显。

因此下一阶段不应继续堆输出功能，而应先把输入与整理工作台做顺。

## 反馈归纳

### 1. 首页和入口

- 第一次打开不知道系统该从哪里开始。
- 页面信息密度偏高，用户需要研究每一块是什么。
- 需要更明确的大动作入口，而不是多个同级小入口。

### 2. 资料上传

- `读取本人资料` 未选择文件时不应触发浏览器原生日文提示。
- 读取精度需要提升，但更直接的体验问题是读取后信息太多，用户不清楚哪些成功、哪些失败。
- 上传后应先显示读取结果：成功读取的值、未读取成功的字段、下一步补录入口。

### 3. 整理信息

- 缺失项不好找，需要持续滚动。
- 当前没有 Excel 式的整体完成视角。
- 录入时应该同时看到整体信息状态和当前输入位置。
- 保存动作不应依赖右上角统一按钮；每个发生编辑的信息卡应出现自己的保存按钮。

### 4. 输出文件

- 输出申请书路径不清楚。
- 用户没有顺利找到“选择案件、选择模板、预览、生成 PDF”的路径。

### 5. 术语和文案

- 当前产品词汇需要集中审校。
- 目标流程应接近游戏本地化工作：导出文本表，业务人员审校/替换，再导入系统。

## 选择方案

采用 B 方案：工作台重构版，但分阶段实施。

不采用一次性大重构。原因是当前公共测试系统仍需稳定运行，所有修改必须先在开发分支验证，再决定是否并入主测试系统。

## 执行切片

### Slice 1：阻塞修复与术语资产化

- 修复上传本人资料未选文件时的浏览器原生报错。
- 增加 UI 术语导出脚本。
- 生成可审校 CSV，区分：
  - 已在 i18n 中的文案。
  - 仍硬编码在页面和组件里的文案。

验收标准：

- 未选文件提交时显示产品内提示，不出现浏览器原生日文气泡。
- 可以通过 `npm run terms:export` 导出审校表。
- 审校表能定位每条文案来自哪个文件和行号。

### Slice 2：首页入口收敛

- 首页只承担两件事：
  - 快速进入输入/整理。
  - 快速进入输出。
- 大动作入口不超过 3 个。
- 首页不能暴露内部工作流术语。

验收标准：

- 新用户 10 秒内能判断下一步该点哪里。
- 输出申请书路径可从首页直接进入。

### Slice 3：整理工作台两区结构

- 左侧：案件/主体/物件/资料的整体状态和完成度。
- 右侧：当前要补录或确认的信息卡。
- 未填写、待确认、不一致永远优先展示。
- 已确认项目自动后排。

验收标准：

- 用户能一眼看到哪些已填、哪些未填。
- 保存单个字段后，该卡片状态更新并回到对应排序位置。
- 来源证据默认折叠，不压迫主录入区。

当前执行记录：

- `整理信息` 入口的对象列表先做轻量改造，不一次性推翻整页。
- 中央区域从解释型卡片改为表格式资料列表，主列表只保留状态、对象、类型、关联、更新时间和操作。
- 处理原因和下一步操作放到右侧详情栏，避免每一行重复展示大段解释。
- 排序规则调整为：待补全、未归属优先，已整理对象后排；同状态下按更新时间倒序。
- 案件详情页字段排序规则同步收紧为：缺值最前，待确认/冲突/不明其次，AI 候选再次，已确认/已修正后排，不适用最后。
- 案件详情页改为字段卡片内保存：字段发生编辑后才出现本卡保存按钮，不再依赖右上角统一保存。
- 修复单卡保存触发 `Illegal invocation` 的 view transition 包装问题，保存动作回到标准 server action 提交流程。
- 保存状态规则收紧：用户在单卡确认同一个值时，也会把 `待确认/不明/不采用/不适用` 等旧状态改为 `已确认`，从而在刷新后排到未完成项后方。
- 移除整理区顶部的批量确认入口，避免“单卡保存”和“批量确认”两个保存模型并存。

### Slice 4：上传读取结果页

- 上传完成后先展示读取结果，不直接把用户丢进大量字段卡。
- 读取成功项和读取失败项分区。
- 读取失败项提供立即补录入口。

验收标准：

- 用户能明确知道这次上传读到了什么、没读到什么。
- 用户可以从失败项直接补录，不需要重新搜索字段。

当前执行记录：

- `InputExtractionReview` 改为先展示读取结果概览：已读取、需补充、低置信三类数字。
- 字段排序调整为：空值优先，低置信其次，已读取后排。
- `全部采用` 调整为更保守的 `采用已读取项`，空值不会被误标为可用。
- 读取结果顶部不再使用大段系统说明，改为文件名、资料类型和结果状态。
- 保存位置区保留，但文案改为业务语言，避免“轻量案件”“自动注册”等内部表达。
- 上传 Excel / 本人资料时，未选文件、文件类型不对、文件过大、空 Excel、读取失败等用户输入错误改为页面内提示，不再进入 Next.js 错误页。
- 页面提示增加错误态，上传类错误用红色提示，成功读取仍用绿色提示。

### Slice 5：读取结果页产品语言收敛

- 将读取结果页的系统视角词汇继续收敛为业务动作语言：
  - `候选值` 改为 `读取内容`。
  - `低置信` 改为 `需复核`。
  - `置信度` 改为 `读取参考`。
  - `匹配字段` 改为 `相同内容`。
  - `需要确认的差异` 改为 `不同之处`。
- 拆分状态文案和按钮动作文案：
  - 状态标签保留为 `待核对 / 已采用 / 已修正 / 暂缓 / 不保存`。
  - 按钮动作使用 `按此内容保存 / 手动修正 / 暂时不清楚 / 不保存`。

验收标准：

- 用户看到的是“读取了什么、是否采用、哪里不同”，而不是工程或模型内部状态。
- 状态标签和操作按钮不再混用同一套文字。

### Slice 6：术语审校回填闭环

- 增加 `npm run terms:import`：
  - 默认 dry-run，只报告可回填数量，不写文件。
  - 使用 `-- --write` 才会更新 `src/lib/i18n.ts`。
  - 只回填 `source=i18n` 且 `suggested_text` 非空的行。
  - `source=hardcoded` 的行只报告，不自动替换。
  - 如果 CSV 的 `current_text` 与源码当前值不一致，跳过并提示过期，避免拿旧审校表覆盖新版本。
- 增加 `docs/operations/UI_TERMINOLOGY_WORKFLOW.md`，说明导出、审校、dry-run、回填、验证流程。

验收标准：

- 业务审校人员只需要编辑 CSV 的 `suggested_text`。
- 工程侧可以先 dry-run，看清楚会改哪些 i18n 文案。
- 不会自动改硬编码组件文本，避免破坏代码结构。

### Slice 7：输出中心路径收敛

- 输出中心当前先围绕保证会社申请书形成清晰闭环：
  - 先选择案件。
  - 再选择保证会社。
  - 最后进入缺失项补齐、预览或下载。
- 未选择案件时，案件列表不再只显示标题和日期，而是直接显示该案件对当前保证会社申请书的未完成项数量。
- 已选择案件时，顶部增加当前输出路径状态：案件、保证会社、预览准备状态。
- 旧的物件概要书、提案、费用明细等输出能力保留在辅助区域，不再抢占当前主路径。

验收标准：

- 用户进入输出中心后能先判断是否需要选案件。
- 用户选案件前能看到哪个案件已经可预览、哪个案件还有缺失项。
- 用户选案件后能明确下一步是补缺失项、选保证会社，还是进入 PDF 预览。

### Slice 8：术语审校优先表

- 在全量术语表之外，增加 `docs/operations/ui-terminology-starter-review.csv`。
- 优先表控制在 300 条以内，只放入口、导入、整理、案件、输出、读取结果这些主链路里的高曝光文案。
- 优先表排序规则为：先列可直接回填的 i18n 文案，再列高频硬编码迁移候选，避免第一轮审校只改到暂时无法自动导入的代码文本。
- 全量表继续保留：
  - `ui-terminology-core-review.csv`：全部前台文案。
  - `ui-terminology-review.csv`：工程全量清单。
- `terms:import` 可通过 `--csv docs/operations/ui-terminology-starter-review.csv` 从优先表 dry-run 或回填。

验收标准：

- 业务人员可以先审校一张较小的表，不需要第一轮处理两千多条。
- 工程侧仍能保留全量清单，后续迁移硬编码文案时不丢项。
- 优先表和全量表使用同一套列结构，避免额外学习成本。

### Slice 9：首页资料地图与主链路术语降噪

- 首页从“任务看板”收敛为“资料管理中心”：
  - 顶部只保留搜索和两个主动作：新建案件 / 补充资料、输出文件。
  - 中间展示案件、客户/关系人、物件、导入资料四条资料线。
  - 下方保留资料索引和当前选中项目，不再展示伪任务系统或申请书专项大板块。
- 首页右侧详情移除“当前卡点 / 建议动作”这类内部工作流语言。
- 导入中心、读取结果和输出中心继续清理前台术语：
  - `系统判断` 改为 `初步对应`。
  - `问题码 / 校验` 改为 `问题汇总 / 检查`。
  - `候选值` 改为 `读取内容` 或具体确认动作。
  - `模板版本 Top / 命中率` 改为面向用户的范本使用情况。
  - 隐藏申请资料详情中的模板版本、文件哈希、匹配度等内部调试信息。
- 保留代码里的字段名、变量名和内部数据结构，不为了文案清理做高风险重构。

验收标准：

- 首页第一屏表达清楚：从哪里录入、从哪里输出、目前有哪些资料对象。
- 主链路页面不再出现模型、系统、问题码、候选值、哈希、匹配度等内部视角词。
- `npm run lint` 通过。

### Slice 10：整理中心去任务化与建档导入入口分层

- 整理中心不再把资料对象描述成“任务 / 卡点 / 下一步”：
  - `资料列表` 改为 `资料索引`。
  - `处理内容` 改为 `当前状态`。
  - `下一步` 改为 `可执行操作`。
  - 右侧详情卡从红色警示样式改为中性状态说明，避免把所有对象都呈现成异常。
- 整理中心的状态说明不再围绕保证会社申请书输出：
  - 案件、主体、物件分别描述自身资料是否完整。
  - 输出检查保留在输出中心，不再塞回信息整理页。
- 建档导入页把“新建对象”和“读取文件”拆成两个层级：
  - 顶部只负责选择要建立的对象：案件、主体、物件。
  - 文件读取改成辅助入口，跳到下方资料读取区。
  - 用户可以不上传资料直接建档，也可以已有文件时先读取再归属。
- 详细设置里的旧版本词汇同步降噪：
  - `任务名称` 改为 `资料名称`。
  - `导入任务历史` 改为 `资料导入历史`。
  - `重试任务` 改为 `重新读取`。
  - `服务请求` 在导入目标里改为 `跟进记录`。

验收标准：

- 用户不会把上传文件理解成新建案件的必要前置条件。
- 整理中心只承担“找对象、筛对象、继续整理”的职责，不承担输出检查。
- 主链路扫描不再命中本轮清理的内部词：`任务名称 / 导入任务 / 重试任务 / 服务请求 / 系统判断 / 问题码 / 候选值 / 哈希 / 匹配度`。
- 修改仍只存在开发分支，未合入主测试系统。

验收标准：

## 术语审校工作流

第一阶段先导出：

```bash
npm run terms:export
```

生成：

```text
docs/operations/ui-terminology-review.csv
docs/operations/ui-terminology-core-review.csv
```

CSV 字段：

- `id`: 稳定条目 ID。
- `surface`: `frontstage`、`system`、`library` 或 `secondary`。
- `source`: `i18n` 或 `hardcoded`。
- `file`: 来源文件。
- `line`: 来源行。
- `occurrences`: 同一文案出现次数。
- `locale`: 当前语言。
- `key`: i18n key，硬编码文案为空。
- `current_text`: 当前文案。
- `suggested_text`: 审校后建议文案。
- `notes`: 是否可直接回填，或需要先迁移到 i18n。

重要边界：

- 第一轮业务审校只看 `ui-terminology-core-review.csv`。
- `ui-terminology-review.csv` 是工程全量清单，用来后续迁移硬编码和错误提示，不适合直接丢给业务审校。
- `i18n` 文案可以进入后续自动回填流程。
- `hardcoded` 文案必须先迁移到 i18n，不能直接靠 CSV 替换代码文本。
- 不允许在组件里继续新增大段硬编码中文/日文/韩文文案。

### Slice 14：建档入口命名与资料读取边界收口

背景：

- 朋友测试后暴露出“上传资料/导入资料/建档导入”混用的问题。
- 当前产品定位不是单纯上传文件，而是先创建或选择业务对象，再把资料读入并归属。
- 如果导航仍叫“上传资料”或“导入资料”，用户会误以为没有文件就不能开始建档。

本轮调整：

- 入口命名统一为：
  - 中文：`建档入口`。
  - 日文：`作成・資料登録`。
  - 韩文：`등록 입구`。
- 首页、导航、模板管理和整理中心同步改掉旧词。
- `导入资料 / 取込資料 / 가져온 자료` 改为 `资料文件 / 資料ファイル / 자료 파일`。
- 文件处理区明确为“已有文件时从这里开始”，不再和新建案件、新建主体、新建物件混成同一个动作。
- 旧的重复快捷入口块已经删除，避免首页和建档页出现两个含义接近的入口。
- 动作反馈里的“导入/取込/가져오기”改成“读取/保存/确认”，用户不再看到映射、导入任务等实现词。
- 种子数据和默认资料名同步清理，避免测试环境历史记录继续露出旧词。

验收标准：

- `src/app`、`src/components`、`src/lib` 中不再命中本轮高风险旧词：
  `作成・取込 / 資料取込 / 取込状態 / 建档导入 / 导入资料 / 资料导入 / 등록·가져오기 / 가져온 자료 / 자료 가져오기 / 가져오기 / 通用导入 / 汎用取込 / 取込`。
- 用户即使没有文件，也应理解可以先建案件、主体或物件。
- 用户已有文件时，可以从同一入口读取资料，再在确认页归属到业务对象。
- 修改仍只存在开发分支，未合入主测试系统。

### Slice 15：建档入口后的新建承接

背景：

- 入口只改名还不够，用户点“新开案件 / 新建主体 / 新建物件”后，必须进入对应的新建页面。
- 新建入口不能隐含“必须先上传文件”。现实业务里经纪人可能只有一个姓名、一个物件名或一个模糊线索，也应该能先建档。
- 浏览器原生必填气泡会破坏产品内反馈一致性，尤其不适合当前的建档入口。

本轮调整：

- 建档入口的三类新建卡片统一带来源参数：
  - `/cases/new?from=entry`
  - `/parties/new?from=entry`
  - `/properties/new?from=entry`
- 案件、主体、物件新建页根据来源显示“返回建档入口”，不再把从入口进入的用户带回普通列表或整理页。
- 主体新建允许空名称提交，系统会生成默认主体名，避免“只有一个联系人线索”时无法建档。
- 物件新建移除物件名的浏览器原生必填校验，空名称由服务端默认名承接。
- 资料记录列表从“最近上传的资料”改为“最近读取的资料”，把文件传输动作和业务资料记录区分开。

验收标准：

- 用户没有文件也可以从建档入口直接创建案件、主体或物件。
- 新建页的返回路径符合用户来源，不把用户带到不相关页面。
- 新建主体和新建物件不会因为空名称触发浏览器原生必填气泡。
- 文件区可以保留“上传文件”的控件语义，但资料记录和业务对象不再叫上传记录。
- 修改仍只存在开发分支，未合入主测试系统。

## 当前不做

- 不直接修改主测试系统。
- 不先追求 OCR 精度大升级。读取精度重要，但当前更大的问题是读取后的呈现和补录闭环。
- 不把输出检查继续塞进整理信息页。输出检查只属于输出中心。

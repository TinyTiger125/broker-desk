## 0. 设计目标与硬边界

本切片只证明一条可回退的最小链：一个非生产经营主体、一页客户空白 PDF、文本/日期/复选框三个字段、公司自建蒙板 v1/v2、普通成员预览和生成文件。平台蒙板目录、八角色迁移、全部字段类型、多页文件、真实资料自动检测和商业上架均不在本切片。

普通成员在本切片及第一版产品中始终不能移动坐标或进入蒙板编辑入口。坐标放置、绑定、测试和发布只由公司表格管理员执行。

TASK-037 当前没有可重复旧流程 PDF 样本。有限实现可以在服务端开关默认关闭、仅允许指定非生产经营主体的前提下开始；实现前先固定静态专项检查和代码事实。旧流程实际 PDF 样本是合并、预发布验收、部署和发布前的硬门；没有样本时不得声称没有回归、不得合并、不得部署或发布。

## 1. 客户空白 PDF 的保存与隔离

### 目标行为

公司表格管理员上传一份明确声明为空白且有权使用的 PDF。服务端可靠拒绝损坏、加密、密码保护和不支持文件；不承诺自动识别所有真实客户资料。文件只属于当前经营主体，普通成员只能在已发布版本的输出流程中间接使用。

### 现有能力与缺口

仓库已有 `attachments`/私有 blob 的租户和用户范围读写能力，但这些对象没有证明能够表达“客户空白表格版本”、页面指纹、版本状态或与蒙板发布版本的不可变关系。不能把普通附件或 `tenant_guarantee_template_installs` 直接冒充新的空白表格对象。

### 确定方案（对象关系已进入有限实现；migration 仅创建/审查，不应用）

客户空白表格使用两层对象，而不是把每个 PDF 当作互不相关的文件：

- `guarantee_blank_forms`：经营主体拥有的逻辑表格，保存 `id`、`tenant_id`、名称、接收方/用途、`active_version_id`、创建/归档时间和操作者；
- `guarantee_blank_form_versions`：同一逻辑表格的不可变文件版本，保存 `blank_form_id`、`tenant_id`、`attachment_id`、`uploaded_by_user_id`、`version_number`、`sha256`、`file_size_bytes`、`mime_type`、页数、页面尺寸、状态和状态操作者。

替换 PDF 时只为同一个 `blank_form_id` 增加新版本并移动活动版本指针；不会创建第二张逻辑表格。新版本不得自动继承旧蒙板的 `exact` 结果，必须重新计算或进入校准。版本唯一约束为 `(blank_form_id, version_number)`；`tenant_id + sha256` 只建立检索索引，不做跨逻辑表格的唯一约束，因此同一经营主体可以在不同业务表格记录中合法复用相同字节。

文件状态只允许 `uploaded`、`ready`、`rejected`、`archived`。文件内容不进入平台公共目录，不由 Broker Desk 分发给其他经营主体。这里已经确定采用“新对象保存逻辑表格/版本元数据、现有私有附件/blob 保存字节”的组合；不是把普通附件行临时解释成空白表格版本，也不是在页面层拼接第二套文件存储。旧附件仍按旧路径读取，新对象只在切片开关打开且租户在 allowlist 内时读写。

### 公司蒙板与逻辑表格归属

`guarantee_company_masks` 归属于 `blank_form_id`，唯一键为 `(tenant_id, blank_form_id)`；其 `active_version_id` 指向公司蒙板版本。`guarantee_company_mask_versions` 的每个版本同时锁定 `blank_form_id` 和具体 `blank_form_version_id`。因此同一张逻辑表格替换 PDF 后，蒙板逻辑对象仍可追溯，但新 PDF 版本必须产生新的匹配结果，不能直接复用旧 `exact`。

### 所有权与私有文件访问

客户空白表格、公司蒙板和已生成文件均归经营主体，不归上传者或最后操作者。`uploaded_by_user_id`、`actor_id` 只记录操作者；上传者离职或停用不使公司对象失效。已生成文件还必须绑定 `case_id`。

现有 attachment/blob 适配为服务端能力而不是把存储路径暴露给客户端：

- 公司表格管理员在同一 `tenant_id` 且具有表格管理能力时，可以查看和管理客户空白表格原件；
- 普通成员不能直接下载客户上传的空白原件，也不能通过 attachment URL 绕过权限；
- 普通成员只有在拥有案件读取权限和输出权限时，才能由服务端生成流程间接使用该表格；服务端同时验证经营主体、已发布蒙板版本、匹配状态和案件权限；
- 历史 PDF 下载同时验证经营主体、案件读取权限和输出查看/下载权限，不检查上传者个人权限；
- 旧的个人维度输出继续按旧字段兼容读取，不在本切片猜测迁移为公司对象。

所有新对象的读取条件都是 `tenant_id` 加对象权限：表格原件是管理员能力，蒙板草稿/发布是模板管理能力，历史输出是案件读取能力与输出权限的交集；不能把 `tenant_id + user_id` 当作公司隔离规则。

## 2. 公司自建蒙板草稿、v1、v2 与活动版本

### 版本关系

```text
客户空白表格版本
        ↓
公司自建蒙板草稿
        ↓ 测试通过并发布
公司自建蒙板 v1（不可变）
        ↓ 修改后另行发布
公司自建蒙板 v2（不可变）
        ↓
活动版本指针只指向 v1 或 v2
```

草稿不能被普通成员读取或使用；发布失败不移动活动指针。v2 发布后，v1 仍可被历史输出引用，不能原地覆盖。

### 确定方案（对象关系已进入有限实现；migration 仅创建/审查，不应用）

选择独立的两层对象，不复用 `guarantee_application_drafts`（案件填写草稿）：

- `guarantee_company_masks`：一个经营主体对一张逻辑客户空白表格的公司蒙板，唯一键为 `(tenant_id, blank_form_id)`，保存 `active_version_id` 可空。
- `guarantee_company_mask_versions`：不可变发布版本和一个草稿版本，唯一键为 `(mask_id, version_number)`；同一 `mask_id` 同时最多一个 `draft`，发布版本状态为 `published` 或 `archived`。

版本记录字段固定为：

- `id`、`mask_id`、`tenant_id`、`blank_form_id`、`blank_form_version_id`；
- `source_platform_mask_id`（从零制作时为 `NULL`）；
- `version_number`、`status`（`draft`、`published`、`archived`）；
- `field_catalog_version`；
- 不含原始 PDF 的坐标、字段绑定、格式和校验快照；
- 创建者、发布者、创建/发布时间及变更说明。

发布在事务中追加不可变版本并更新 `guarantee_company_masks.active_version_id`；活动版本是服务端指针，不是客户端可以提交的任意版本号。发布失败时指针不变，v1/v2 内容不被覆盖。

### 确定的表格—蒙板匹配关系

匹配不是客户空白表格的状态，而是独立对象 `guarantee_mask_matches`：

- 唯一键：`(tenant_id, blank_form_version_id, mask_version_id)`；
- `status`：`exact`、`needs_recalibration`、`incompatible`、`unknown`；
- `evaluated_at`、`evaluated_by_user_id`、原因和参与计算的文件/版本指纹。

发布前由公司表格管理员触发服务端计算并要求 `exact`；重新确认也只允许公司表格管理员，普通成员不能触发。客户空白表格版本、蒙板版本或字段目录版本变化时，旧匹配自动失效为 `unknown` 或 `needs_recalibration`，不得继续沿用 `verified` 等模糊状态。

## 3. 文本、日期、复选框与案件字段绑定

本切片只支持三类字段：

| 蒙板字段 | 案件字段来源 | 保存内容 | 校验 |
|---|---|---|---|
| 文本 | 现有案件字段目录中的文本字段 | `field_id`、坐标、格式/长度规则 | 字段存在、值可格式化、不得越过案件权限 |
| 日期 | 现有案件字段目录中的日期字段 | `field_id`、日期格式、坐标 | 日期格式、空值和显示格式 |
| 复选框 | 现有案件字段目录中的布尔/枚举字段 | `field_id`、选中/未选规则、坐标 | 允许值集合与默认空值规则 |

蒙板只保存字段 ID、位置、格式和校验，不保存第三方原始 PDF。发布时锁定 `field_catalog_version`；字段目录不兼容时，版本进入待重新验证，不继续正式输出。

### 确定的唯一坐标模型

复用现有 PDF 布局运行时的坐标体系，固定为 `pdf_points_bottom_left_v1`：每个字段至少保存 `page_number`、`x`、`y`、`width`、`height`，单位为 PDF points，原点为页面左下角。现有编辑器使用的“从页面顶部计算”只是输入辅助，保存前必须按页面高度转换为该唯一底部原点坐标；浏览器缩放、CSS 像素和设备像素比只影响编辑器显示，不写入坐标值。

文本、日期和复选框都使用同一 `page_number + box` 解释；最终 PDF 渲染器直接消费该模型，预览和正式生成共用同一坐标转换逻辑。客户空白表格版本的页面尺寸或方向变化时，匹配关系必须失效并重新校准，不能把旧坐标直接套到新尺寸。切片不要求多页编辑体验，但页码从对象结构开始就是必填，不能永久省略。

普通成员输出时只读取案件中的权威事实；页面允许填写的仅是本次申请书专属补充数据。补充数据只进入 `guarantee_preview_confirmations`、申请书草稿和最终输出快照，不写回案件事实。姓名、地址等案件事实有误时，页面必须返回案件流程修正，再重新预览；输出页面不得以“补齐字段”为名直接更新案件。

## 4. 普通成员与管理员的服务端权限区分

### 本切片权限

- 管理员：暂复用既有 `tenant_owner`，允许上传客户空白 PDF、创建草稿、放置/绑定字段、测试、发布 v1/v2、回退活动版本。
- 普通成员：沿用现有 `output.preview`、`output.download_final` 能力，只能选择已发布版本、填写本次申请书专属补充数据、预览和生成文件；不得从输出页面改写案件权威事实。
- 普通成员：没有 `template.edit_draft`/`template.publish`，没有坐标编辑入口。

服务端必须继续使用 `requireTenantSession`、租户范围案件读取和权限检查。隐藏字段、URL 参数和客户端状态不能授予模板管理权。本切片不新增正式角色、不完成“可管理公司表单配置”预设迁移。

运行验证必须同时提供同一非生产经营主体内的两个合法权限上下文：一个 `tenant_owner`（或已获批准的管理员）上下文，以及一个普通成员上下文。它们可以是两个内部测试身份，也可以是经审查的服务端权限测试加浏览器身份组合，但不得通过客户端参数切换角色，也不要求产品负责人提供账号、Cookie 或 Token。只有管理员上下文能看到坐标编辑入口并调用草稿/发布服务端动作；普通成员即使直接请求管理 URL 或伪造字段，也必须在服务端被拒绝。

## 5. 可关闭隔离边界

仓库当前没有可复用的保证申请书新流程 feature flag。`legacy_development` 仅是非生产布局 fallback，不是开关。

### 确定方案

切片 1 采用“部署默认关闭 + 明确非生产测试经营主体 allowlist”的服务端组合边界。配置名固定为 `GUARANTEE_G1_SLICE1_ENABLED` 与 `GUARANTEE_G1_SLICE1_TENANT_ALLOWLIST`；本文件只确定合同，不创建配置或修改代码：

1. 只在服务端读取，客户端不能打开；
2. 默认关闭，只有指定非生产租户和明确测试环境可用；
3. 关闭后新上传、蒙板管理和新输出入口不可达；
4. 旧预览、旧下载、旧租户安装和历史输出不被删除或覆盖；
5. 关闭动作可在不改数据库内容的情况下执行，并留下操作记录。

服务端守卫同时检查部署环境、allowlist 租户、当前成员和能力；没有四者交集即按旧入口或明确不可用状态返回。切片关闭时不访问新对象，回滚只需关闭配置并恢复旧入口，不能通过客户端状态绕过。

## 6. 预览与正式生成的同一版本关系

### 确定方案：服务端预览确认记录

不采用客户端版本号，也不采用仅由客户端持有的签名令牌。预览确认使用新对象 `guarantee_preview_confirmations`，由服务端生成不可猜测的 opaque ID，并保存一次不可变的确认上下文：

- `id`、`tenant_id`、`actor_user_id`、`case_id`；
- 案件事实版本或输入快照哈希；
- 客户空白表格版本 ID 与 SHA-256；
- 公司蒙板版本 ID 与版本号；
- 字段目录版本；
- 申请书专属补充数据快照及哈希；
- `expires_at`、`status`（`issued`、`processing`、`consumed`、`expired`）、`processing_expires_at`、一次性 `processing_token`、创建和消费时间、最终 `generated_output_id`。

预览时服务端根据当前活动版本和匹配关系创建该记录；客户端只收到 opaque ID。正式生成只接受该 ID，不接受任意版本号或客户端自带快照。服务端再次校验租户、成员、有效期、状态，以及案件事实、空白表格、蒙板、字段目录和补充数据的当前哈希。任何一项变化都返回 `preview_stale`，要求重新预览，不静默换用 v2。过期记录永不重新激活。

正式生成先以数据库原子更新或等价行锁取得唯一执行权：`issued → processing`，并写入 `processing_expires_at` 和一次性 `processing_token`。只有持有该令牌的请求可以完成、消费或释放确认；租约过期后旧请求不能清理新请求的占用。`generated_outputs.preview_confirmation_id` 具有唯一约束。并发的第二个请求取得不到执行权时只返回“生成处理中”状态，不渲染、不写文件；若同一 confirmation 已是 `consumed`，服务端直接返回其 `generated_output_id` 对应的已保存文件，不再次渲染；若渲染或文件写入在尚未建立输出记录时失败，则把未过期的 `processing` 安全恢复为 `issued`，允许重试。处理租约超时只能由服务端恢复为 `issued`，不能跳过校验。最终输出记录写入与 confirmation `processing → consumed`、`generated_output_id` 写入在同一数据库事务中完成。

预览和正式生成都使用已锁定上下文中的同一服务端 layout/value resolver：

```text
confirmation record (immutable snapshot)
        ↓
同一 layout/value resolver
        ├─ 预览：不写正式输出
        └─ 正式生成：写入不可变输出记录和实际 PDF
```

不能让预览读取 v1、下载读取 v2，也不能从客户端传入的版本号绕过活动版本和指纹匹配。匹配状态不是“有图就继续”：无法匹配、需要重新校准和不兼容均应阻断普通成员生成。

## 7. 已生成文件的不可变快照与实际 PDF 保存

### 确定方案：保存实际 PDF 字节

正式生成必须把最终 PDF 字节写入租户私有文件存储。物理字节复用现有私有 attachment/blob 能力；`generated_outputs` 增加并固定以下一等字段（字段名为技术合同，是否拆列由获授权实现保持同语义）：

- `file_attachment_id`（指向私有文件引用，唯一）；
- `file_sha256`、`file_size_bytes`、`file_mime_type`（必须为 `application/pdf`）；
- `file_status`（成功输出记录固定为 `ready`）；
- `blank_form_version_id`、`blank_form_sha256`；
- `company_mask_version_id`、`field_catalog_version`；
- `preview_confirmation_id`（唯一）；
- 案件事实版本或输入快照哈希；
- 补充数据快照及哈希、操作者、租户、生成时间和审计引用。

生成顺序固定为：原子占用 confirmation → 使用其中快照渲染 → 计算 SHA-256/大小 → 在租户私有存储暂存并取得文件引用 → 在同一数据库事务写入带快照的 output 记录、将 `file_status` 设为 `ready`、写入 confirmation 的 `generated_output_id` 并标记 `consumed`。因此 `generated_outputs` 不创建永远停留的 `pending` 或 `failed` 成功记录；文件或事务失败只产生失败审计/可恢复孤立文件记录，不产生“生成成功”输出。输出元数据事务失败时删除未绑定文件和附件引用，删除失败则登记可恢复的孤立文件清单（租户、临时键、哈希、时间、原因），仍不得宣称成功。历史文件读取 `file_attachment_id` 对应的当时字节，不重新使用当前蒙板或渲染代码生成。

历史下载每次都重新执行租户、成员能力和文件引用权限检查。v2 发布只追加新版本和新输出，不能覆盖 v1 的文件引用、哈希、大小、快照或内容。旧的 metadata-only 输出如果没有文件引用，必须如实显示为无可下载文件，不补造 PDF。

### 不可变业务快照

正式生成至少需要固定：

- 经营主体和操作者；
- 客户空白表格版本 ID 与文件指纹；
- 公司自建蒙板版本 ID/版本号；
- 字段目录版本；
- 案件事实版本或不可变输入快照；
- 申请书补充数据快照和哈希；
- 实际 PDF 的私有文件引用、SHA-256、大小、MIME 类型、生成时间和审计记录。

`generated_outputs` 的上述字段是确定合同，不把“JSON 里可能存在”当作一等追溯。任何结构变化都必须兼容旧数据、支持关闭切片和回滚；本轮只创建追加式 migration 文件并审查，不应用到任何数据库。

## 8. 现有数据兼容、双读与回滚

兼容原则：


1. 旧五套平台蒙板、旧租户安装和旧输出继续按当前代码路径读取；新公司自建对象不覆盖旧对象。
2. 新入口只在服务端隔离边界打开；关闭后旧入口和旧数据仍可读。
3. 新记录在 memory/PostgreSQL 适配层都实现同一组对象、状态、唯一约束和租户过滤语义；memory 使用隔离的私有文件替身或字节存根，但仍保存同一文件引用、哈希、大小、MIME 和不可变版本关系，不另造测试专用业务语义。PostgreSQL 使用上述新增对象和现有私有 blob 能力。
4. 旧输出没有空白表格指纹时保留为空或标记未知，不回填猜测值。
5. 新对象采用追加版本，不做破坏性重写；必要的唯一约束为：空白表格版本 `(blank_form_id, version_number)`、逻辑蒙板 `(tenant_id, blank_form_id)`、蒙板版本 `(mask_id, version_number)`、匹配关系 `(tenant_id, blank_form_version_id, mask_version_id)`、`generated_outputs.preview_confirmation_id` 唯一和实际文件引用唯一。`tenant_id + sha256` 只建索引，不作为跨逻辑表格去重约束。失败回滚只移动活动指针、标记草稿/匹配状态、恢复 confirmation 或关闭新入口。
6. 旧输出不做回填；历史 metadata-only 记录继续可审计但不被伪装成可下载文件。关闭新入口不会删除新对象或历史 PDF。
7. 合并前必须用受控预发布环境固定一份旧流程基线输出，并证明关闭新流程后该基线仍可读取。

## 9. 受控预发布验证顺序

运行验收门：由项目运行环境提供同一非生产经营主体内的两个合法权限上下文：一个 `tenant_owner` 或已批准管理员身份，以及一个普通成员身份。可以是两个内部测试身份，也可以是经审查的服务端权限测试加浏览器身份组合；不得通过客户端切换参数伪造角色，不要求产品负责人提供凭据，不要求第二租户。两个上下文是运行验收门，不阻断在默认关闭、单租户隔离下编写实现或先做服务端权限测试。旧流程实际 PDF 样本仍是合并、预发布验收、部署和任何发布行为之前的硬门。

验证顺序：

1. 在明确 Git SHA 的受控预发布环境固定一份旧流程预览/生成文件，并保存脱敏证据和哈希；
2. 确认新流程开关默认关闭时旧流程仍可用；
3. 只对一个测试经营主体启用切片 1；
4. 用管理员上下文上传、放置/绑定三字段、测试并发布 v1；
5. 用普通成员上下文从案件预览并生成文件 v1，同时验证管理 URL、坐标动作和发布动作均被服务端拒绝；
6. 用管理员上下文发布 v2，确认 v1 的实际 PDF 字节、SHA-256、文件引用和版本记录不变；
7. 用普通成员重新生成时只能使用 v2；打开历史记录时读取已保存的 v1 文件，不重新渲染；
8. 关闭切片 1，确认旧流程、旧入口和历史文件仍可读；
9. 失败或无法取得旧样本时，停止合并/发布验收，不把静态检查替代真实运行证据。

## 11. 技术设计交付判断

本文件回答了 TASK-038 的技术设计问题，并将对象、版本、匹配、文件、确认上下文、权限上下文、memory/PostgreSQL 语义、唯一约束、回滚和预发布门收敛为确定方案。产品负责人已授权一次默认关闭、单非生产经营主体 allowlist 的有限实现；本授权不包含 migration 应用、合并、部署、商业上架或旧平台蒙板生产行为变更。

## 12. 一页决策摘要

### v1 为什么不会随 v2 改变

正式生成的 PDF 字节会写入当前经营主体的私有文件存储，`generated_outputs` 同时保存不可变的文件引用、SHA-256、大小、MIME 类型、客户空白表格版本、公司蒙板版本、字段目录版本和案件/补充数据快照。v2 只能追加新蒙板版本和新文件；历史打开直接读取 v1 的已保存字节，不调用当前蒙板或当前渲染代码重新生成。

### 预览与最终生成为什么一定使用同一版本

预览由服务端生成不可猜测的 `guarantee_preview_confirmations` 记录，锁定经营主体、案件事实哈希、客户空白表格版本和指纹、公司蒙板版本、字段目录版本、补充数据快照、操作者和有效期。最终生成只接受该确认记录，重新校验所有哈希和权限；任何变化都要求重新预览，不能静默采用 v2。

### 普通成员为什么无法进入或调用蒙板编辑

管理员和普通成员使用两个服务端权限上下文。只有管理员能力可以读写草稿、坐标、绑定、测试和发布动作；普通成员只可选择已发布版本、填写本次补充数据、预览和生成。管理入口隐藏不是安全边界，直接 URL、客户端参数或伪造字段也会被服务端拒绝；普通成员在本切片及第一版产品中始终不能移动坐标。

### 关闭切片后为什么旧入口和旧数据不受影响

新流程由服务端默认关闭且受非生产经营主体 allowlist 限制。关闭时不访问新对象，不删除旧入口、旧租户安装、旧蒙板或历史文件；旧路径继续按当前代码读取。回滚只关闭守卫或把活动指针退回旧版本，不做破坏性数据重写。旧流程 PDF 样本是合并、预发布和发布前硬门；缺少样本只能阻断这些验收，不能被静态检查冒充通过。

### 已确定的技术选择

- 客户空白表格：`guarantee_blank_forms` 保存逻辑表格，`guarantee_blank_form_versions` 保存不可变 PDF 版本；字节复用私有 attachment/blob；版本状态为 `uploaded`、`ready`、`rejected`、`archived`。
- 公司蒙板：`guarantee_company_masks` 逻辑对象 + `guarantee_company_mask_versions` 不可变版本；活动指针由服务端维护。
- 匹配：独立 `guarantee_mask_matches` 关系，状态为 `exact`、`needs_recalibration`、`incompatible`、`unknown`，不使用 `verified` 替代。
- 预览确认：服务端记录，不采用客户端任意版本号或仅客户端持有的令牌。
- 输出文件：实际 PDF 字节私有保存；`generated_outputs` 保存文件引用和完整版本快照。
- 双读：memory/PostgreSQL 采用同一对象、状态、唯一约束和租户过滤语义；旧 metadata-only 输出不伪装为可下载文件。
- 数据结构：如需新增字段/对象，只允许追加式、可回滚、兼容旧数据的 migration，另行授权后实施。

## 13. 第二次技术设计复核差异摘要

1. 新版 PDF 仍属于同一张公司表格：上传替换只在同一个 `guarantee_blank_forms.id` 下追加 `guarantee_blank_form_versions.version_number`，蒙板逻辑对象归属逻辑表格，具体发布版本锁定新文件版本；旧匹配不会自动继承。
2. 上传者离职后公司仍能使用：对象所有权是 `tenant_id`，上传者字段只作审计；表格原件由公司表格管理员能力读取，蒙板和历史输出按公司权限与案件权限读取，不依赖上传者仍在职。
3. 有案件权限的其他成员可以查看历史文件但看不到原始空白 PDF：历史下载检查 `tenant_id + case read + output view/download`，原始 PDF 直接读取只开放给表格管理员，普通成员只能由服务端生成流程间接使用。
4. 双击只产生一个文件：confirmation 先原子占用为 `processing`，`generated_outputs.preview_confirmation_id` 唯一；已 `consumed` 的重试直接返回 `generated_output_id`，不会再次渲染。
5. 浏览器缩放不改变最终坐标：唯一模型是 PDF points、左下角原点的 `page_number/x/y/width/height`；浏览器只改变显示，编辑器保存前转换到同一 PDF 坐标，预览和正式生成复用同一转换逻辑。
6. 没有旧流程样本时允许做到：可以在默认关闭、单非生产经营主体 allowlist 下编写隔离实现并做静态/服务端权限测试；禁止声称无回归、合并、预发布验收、部署或发布，直到取得旧流程实际 PDF 样本。两个合法权限上下文是运行验收门，不要求产品负责人提供凭据。

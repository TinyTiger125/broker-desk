- 制定日期：2026-08-18

- 外部研究依据：[外部产品模式与采用决策矩阵](./GUARANTEE_APPLICATION_EXTERNAL_PRODUCT_MODE_MATRIX_2026-08-18.md)

## 1. 产品定位

Broker Desk 是以案件事实为核心、兼容不同申请接收方和提交方式的房地产申请工作台。

本专题当前交付的是“指定文件兼容输出”能力。PDF 填写层是没有接口时的兼容手段，不是长期产品边界：

```text
Broker Desk 案件事实
        ↓
申请接收方
├─ 当前：通过兼容填写层生成指定申请书
└─ 未来：通过合作接口直接传送结构化数据
```

本阶段不实现保证公司接口、电子签名、第三方协作系统联携或 Broker Desk 自有表单。未来接口路线不能反向扩大当前 PDF 专题的对象或权限范围。

## 2. G0 对象合同

“模板”不再作为所有对象的统称。第一版使用以下七类对象：

### 2.1 兼容配置目录项

平台维护的说明性记录，包含：适配的保证公司、表单名称、适用版本、页数和页面尺寸、文件指纹和识别特征、最后验证日期、配置状态、兼容性说明。

它不包含第三方原件正文、高清背景图或完整缩略图，也不向客户分发第三方空白原件。

### 2.2 租户空白原件

客户上传并声明有权用于业务的空白 PDF，仅本租户可访问，不自动成为平台公共资产，不得含真实客户资料。第一版不接受加密、密码保护、损坏或其他格式的文件。其存储、指纹、页数、尺寸、保留周期和安全校验必须有独立合同；文件大小、页数上限和页面尺寸公差留给 G1 技术验证，最终保留期限和不可恢复删除属于上线前法律/技术门。

### 2.3 平台基础填写层

平台制作的坐标、字段绑定、字段类型、格式、校验和原件匹配条件，不包含原件背景内容。

### 2.4 租户覆盖层

租户在平台基础层上做出的调整。它不修改平台基础层，有独立版本，只能由获授权成员发布，平台更新不得自动覆盖。

### 2.5 租户自建填写层

公共兼容目录没有匹配配置时，租户从自己的空白原件创建的填写层，仅在本租户使用。

### 2.6 输出快照

每次正式输出记录租户、案件版本、空白原件指纹、平台基础层版本、租户覆盖/自建层版本、输出数据、操作者和时间、最终文件记录。后续修改不得改变历史输出。

### 2.7 适配申请

客户请求平台协助制作配置的记录。客户原件不会因为提交适配申请而自动进入公共目录；如未来升级为公共兼容配置，必须经过独立审核和来源/权利确认。

### 2.8 四类独立权利状态

任何配置必须分别记录：第三方空白原件/完整预览图的公开展示权；第三方空白原件的复制、下载和分发权；Broker Desk 自制填写层/兼容配置的安装和使用边界；租户使用自己上传原件进行内部业务输出的边界。五套现有平台蒙板没有权利证据，因此不向新客户正式上架原始 PDF 或完整图片；它们仍可作为 G1 真实测试样本，并继续支持现有生产行为。平台蒙板是否需要额外授权记录为上线前法律确认，不由产品经理推导。

## 3. 外部产品模式的采用边界

外部模式研究的完整证据、官方来源和访问日期见矩阵文档。本合同固定以下采用决定：

1. **采用 Adobe 的文档与字段层分离**：填写层不含原件内容，可以套用到新上传文件；共享范围先限制在创建者/管理者，测试通过后再发布到本经营主体。
2. **采用 SAP 的 Schema、Template、Data Source、Output Control 分离**：Broker Desk 字段目录是 Schema 级合同，填写层是 Template，案件事实和申请书补充字段是 Data Source，预览/确认/下载是 Output Control 门禁。
3. **采用 DocuSign Rooms 与 Lone Wolf 的案件中心和跨文件复用原则**：普通成员从案件开始，申请书是案件输出载体；同一案件事实可供多份文件复用。
4. **采用日本电子申请产品的一次录入、缺漏检查、接收方/状态可追踪方向**，但当前不实现 At Home、ITANDI 或 いえらぶ的 API/保证公司联携。
5. **采用 Jotform Smart PDF 的原件连接、导入后手动映射和拖动/缩放校准事实**；自动识别只可作为未来候选生成，不是第一版发布门槛。
6. **不采用**电子签名、模板市场、第三方原件公共分发、企业级组织树、保证公司接口、自动画框核心能力、Broker Desk 自有报价单或其他输出专题能力。

五套现有平台蒙板可以保留配置 ID、指纹和历史输出追溯，继续用于 G1 的匹配、校准、预览和输出链路验证，并不改变现有生产行为。它们在法律结论前不正式上架给新客户；公共目录可以为空，但这不是对蒙板永久不能输出的判定。

## 4. 版本链与发布合同

版本链固定为：

```text
平台基础填写层
→ 租户安装
→ 租户覆盖版本或租户自建版本
→ 已发布租户版本
→ 输出快照
```

### 4.1 字段目录版本

每个填写层必须记录其适配的 Broker Desk 字段目录版本。字段目录发生不兼容变化时，相关配置状态变为“待重新验证”，不能用于新的正式输出，直到完成验证并生成新的发布版本。

### 4.2 原件匹配状态

原件与填写层的匹配结果至少为：

| 状态 | 业务含义 | 允许动作 |
| --- | --- | --- |
| 精确匹配 | 原件指纹/版本和填写层适配条件一致 | 可进入正常预览、确认和输出 |
| 需要重新校准 | 可以识别为同一业务表单族，但坐标或字段连接不能直接信任 | 只能进入填写层管理流程；普通成员不得强制输出 |
| 不兼容 | 原件不属于该填写层适配范围 | 停止套用，要求更换原件或填写层 |
| 无法判断 | 现有指纹/特征不足以作出可靠判断 | 停止正常输出，要求管理者确认或重新验证 |

只有“精确匹配”可以直接进入普通成员的正常预览。任何其他状态都必须说明原因和下一步，不得只显示技术错误。

### 4.3 不可变输出

正式输出必须把当时解析出的案件数据、补充字段、原件指纹、字段目录版本、填写层版本和最终文件一起快照化。后续发布、停用、重新校准或平台更新不得改变历史输出。

## 5. 两条完全分离的用户流程

### 5.1 普通成员的案件输出流程

```text
选择案件
→ 选择保证公司
→ 系统选择本经营主体已发布且匹配的填写层
→ 补齐申请书差异字段
→ 预览
→ 确认输出
→ 下载/交付
```

普通成员不需要理解坐标、字段目录版本、原件指纹或租户覆盖层，也不能进入填写层编辑器。

### 5.2 填写层管理者的低频管理流程

```text
上传本租户空白原件
→ 选择并应用已有填写层（如有）
→ 人工校准
→ 使用测试案件预览
→ 检查溢出、复选框、日期和分页
→ 保存草稿
→ 发布给本经营主体
```

新建或修改的配置默认只对创建者和获授权填写层管理者可见。测试未通过、匹配状态不是“精确匹配”或字段目录版本不兼容时，不得发布或输出。

这条流程是低频管理工具，不是普通成员的日常任务，也不是案件 Object Page 的第二套编辑器。

## 6. 权限合同

权限分为三个维度，不以页面直接暴露底层几十项权限：

1. 公司管理权限：成员、订阅和经营主体资料；
2. 业务操作权限：创建、处理、审核和输出案件；
3. 填写层管理权限：创建、修改、发布和停用租户填写层。

第一版至少保证：普通成员只能使用已发布配置；用户端只展示一个“可管理公司表单配置”预设；`tenant_owner` 默认拥有该能力并可授予其他成员；填写层管理者可以编辑和发布本公司配置；`tenant_admin`、`manager` 及其他职务角色不因角色名自动获得；平台配置管理权限与租户配置管理权限分离；平台协助适配只访问申请中明确授权的空白原件和配置对象，限对象、限目的、可撤销、可过期、可审计，不读取客户案件；普通成员不得移动字段坐标，遇到错位只能停止输出并提交填写层管理者重新校准；修改公司填写层是明确动作并生成新版本；不能停用最后一位公司负责人。

现有八种内部角色不在 G0 删除。后续技术合同必须给出旧角色到三个权限维度的兼容映射，并保持已有权限负向验证。

## 7. 当前结构差距与迁移影响

以下是 G0 必须承认的旧结构差距，不是本阶段授权修复：

| 当前结构 | 与目标合同的差异 | 后续处理边界 |
| --- | --- | --- |
| 租户模板页和平台模板页使用“官方模板/官方原件”语义，并展示保证公司图片或源文件名 | 越过“兼容配置”和第三方原件分离边界 | 阶段 1 做来源/权利矩阵；未有证据的内容不得继续作为公开目录 |
| 现有平台发布和租户安装链 | 已有冻结安装快照，但缺少完整租户覆盖/自建流程和四态匹配合同 | 阶段 2/3 定义对象和状态；不在 G0 直接改代码 |
| `guarantee_application_drafts` 含 `user_id` | 与配置/草稿从创建起归经营主体的目标存在冲突 | 阶段 3 设计租户所有、操作者记录和迁移回滚 |
| `generated_outputs` 已有部分版本/输入快照字段 | 尚缺一等租户空白原件指纹/版本合同 | 阶段 3 补齐技术合同，不能由页面层伪造 |
| 成员/账户页面使用席位占用语义 | 与按经营主体订阅、不按席位售卖冲突 | 目标状态不以 `purchased_seat_count` 限制成员；旧字段和计费状态先保留，迁移验证前不解除生产限制；成员页目标不展示席位占用 |
| 现有八角色与模板动作混合 | 尚未映射到公司管理、业务操作、填写层管理三维权限 | 阶段 1 输出兼容矩阵，保留旧角色直到迁移完成 |
| 旧工程文档和静态资源使用“official”表达 | 会让产品合同和法律边界相互矛盾 | 先登记、核对来源与权利，再决定保留、改名或退役 |

### 7.1 对既有 G0/产品合同的具体修改

相对于旧的“选择官方模板 → 使用平台坐标填充 → 输出 PDF”叙述，本修订明确改变以下合同内容：

1. **产品定位**：从 PDF 模板/自动填表工具改为“以案件事实为核心、兼容不同申请接收方和提交方式的房地产申请工作台”。当前 PDF 是兼容路径，未来接口是另一路径。
2. **对象边界**：把第三方原件、兼容配置目录项、平台基础填写层、租户覆盖/自建层和输出快照拆成独立对象；公共配置不得带原件正文或高清背景。
3. **所有权**：租户上传的空白原件、租户草稿和租户发布版本从创建起归经营主体，不归个人账号，也不进入平台公共目录。
4. **版本链**：从单一平台模板扩展为“平台基础填写层 → 租户安装 → 租户版本 → 输出快照”；平台更新不得静默覆盖租户版本。
5. **管理流程**：填写层编辑器从普通成员日常流程移出，改为创建者/获授权管理者的低频工具，采用私有草稿、测试案件、人工校准、明确发布。
6. **匹配门禁**：新增精确匹配、需要重新校准、不兼容、无法判断四态；只有精确匹配进入普通成员正常预览，其他状态必须阻断或转管理流程。
7. **字段目录**：把 Broker Desk 字段目录版本写入填写层发布合同和输出快照；不兼容字段变化自动要求重新验证。
8. **日常案件流程**：普通成员从案件开始，系统选择已发布且匹配的填写层；不要求用户先进入编辑器或理解坐标、指纹和版本。
9. **自动识别**：删除“自动画框/自动绑定是第一版成功条件”的隐含承诺；未来自动识别只能生成候选，不能自动发布或绕过测试。
10. **权限表达**：从页面暴露底层角色/席位语义改为公司管理、业务操作、填写层管理三个维度；旧八角色保留兼容，不在本合同中删除或重建权限系统。
11. **输出事实**：正式输出必须固定案件版本、原件指纹、字段目录版本、填写层版本、操作者和最终文件；旧输出不受后续配置修改影响。
12. **旧文档地位**：`V1_GUARANTEE_APPLICATION_OUTPUT.md`、`PDF_TEMPLATE_AUTHORING_EXPERIENCE.md` 和 `GUARANTEE_TEMPLATE_PUBLICATION.md` 继续作为历史技术/实施背景，不能覆盖本 G0 产品合同；其中“official”文案和静态原件资产必须经过来源与权利复核后再决定处置。

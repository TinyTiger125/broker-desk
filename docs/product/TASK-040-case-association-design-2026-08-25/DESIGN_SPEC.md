# 设计说明与信息架构

## 1. 设计判断

当前页面已经有一套稳定的 Broker Desk 外壳，但“案件”和长期主资料之间的关系仍被压缩成两个原生下拉框与一条关系摘要。这个交互无法同时承载搜索、角色、多次关联、权限解释、快速创建和撤销确认，因此本阶段只补一层“关联工作区”，不重做案件页面。

当前设计的核心判断：

- **案件是工作上下文，人物和物件是独立主资料。** 案件只保存关联，不复制主资料。新建案件页先保存到案件草稿；案件创建成功时才一次性保存案件和全部关联。
- **人物关联是多行、多角色；主要物件是单值。** 一个人物可以同时承担多个固定角色；一个案件最多一个主要申请人和一个主要物件。案件可以暂时缺少主要申请人或主要物件。
- **创建与整理共用同一关联组件。** 创建页采用“内嵌摘要 + 抽屉”；详情页采用“关联资料”章节 + 同样的两个抽屉，避免两套心智模型。
- **写入能力与读取能力分开表达。** 候选列表只返回当前用户拥有可写能力的主资料；资料是仅自己可见还是公司成员可见／只读，不改变本人候选资格。其他成员只有公司成员可见／只读权限的资料不能成为候选。
- **解除是关系操作，不是删除。** 成功后只删除案件关联；人物/物件主资料仍留在其自己的列表、权限与审计中。

## 2. 证据基线与现状问题

设计依据：

- 当前创建页：`src/app/cases/new/page.tsx`。现有 `案件信息` 与 `关联对象` 两个区块，人物和物件均为原生 `<select>`，只显示名称，未提供角色、检索、创建、权限状态或重复提示。
- 当前整理中心：`src/app/organize-center/page.tsx` 与 `src/components/organize-center-object-browser.tsx`。这是现有的 List Report：类型卡、关键词、状态过滤、结果数、分页和行级操作；案件行只有案件链接/保管操作，没有关联管理入口。
- 当前案件详情：`src/app/cases/[id]/page.tsx` 与 `src/components/case-overview.tsx`。详情采用长型 Object Page/字段整理方式，已有关系树入口，但没有一个能解释“人物角色、主要物件、解除不删除”的稳定章节。
- Layout System：`docs/product/BROKER_DESK_LAYOUT_SYSTEM_V1.md`。采用 Shell → Dynamic Page Header → Section/Subsection；列表遵循 List Report；详情遵循 Object Page；表单遵循 Responsive Form；移动端抽屉使用全屏/底部编辑层。

现状问题不是权限缺口，而是信息架构缺口：

| 现状 | 风险 | 设计处理 |
|---|---|---|
| 原生下拉只有名称 | 资料多时无法搜索，无法说明为何不可选 | 抽屉搜索、分组摘要、只列当前用户可关联的候选 |
| 人物只有一个 `primaryPartyId` 入口 | 无法表达多人物、多角色 | 人物关联表格 + 固定角色多选 |
| 物件只有一个字段 | 无法解释主要物件替换与历史 | 单值卡片 + 更换确认 |
| 详情只显示关系摘要 | 不能新增/解除，也不说明关系不会删主资料 | “关联资料”章节、二次确认与成功反馈 |
| 无权限只读语义分散 | 用户可能把“不可选”误解为资料不存在 | 统一状态带；不在候选中列出隐藏记录 |

## 3. 产品权限与动作矩阵

| 身份/对象 | 查看已关联资料 | 新增关联 | 解除关联 | 更换主要物件 | 编辑主资料 |
|---|---:|---:|---:|---:|---:|
| 案件当前负责人且对对象有可写能力 | 是 | 是 | 是 | 是 | 进入主资料页后按主资料权限 |
| 同公司 active 成员，仅有案件或主资料只读能力 | 是（只读） | 否 | 否 | 否 | 否 |
| 公司负责人/表格管理员，但不是当前资料负责人 | 不能绕过资料权限 | 否 | 否 | 否 | 否 |
| 公司负责人/表格管理员，同时本人是当前资料负责人 | 按本人正常可写能力 | 按本人正常可写能力 | 按本人正常可写能力 | 按本人正常可写能力 | 按本人正常可写能力 |
| pending、suspended、removed、跨主体 | 否 | 否 | 否 | 否 | 否 |

候选规则固定为：

1. 当前真实 session、tenant、active membership；
2. 主资料负责人状态明确；
3. 当前用户对该主资料拥有可写能力，无论资料是仅自己可见还是公司成员可见／只读；
4. 不能通过浏览器提交 ID 改写创建者、当前负责人、经营主体或操作者；服务端必须再次校验。

界面只使用产品语言：可写能力显示为“可关联”；公司成员可见权限显示为“公司成员可见／只读”；仅自己可见状态显示为“仅自己可见”。

### 3.1 V1 人物角色合同

固定角色为：

- 主要申请人
- 承租人
- 同住人
- 连带保证人
- 紧急联系人
- 出租人／业主
- 其他关联人

同一人物在同一案件可以拥有多个角色，但同一案件最多一个“主要申请人”。已关联人物进入“编辑角色”，不会建立第二条重复关系。案件创建和案件整理均允许暂时没有主要申请人；保证公司申请书只有在主要申请人、主要物件均已明确关联且当前用户有权使用二者时才可生成。

## 4. 案件页面信息结构

### 4.1 创建案件（Responsive Form）

```text
Shell / Breadcrumb: 信息整理 / 案件 / 新建
└─ Dynamic Page Header
   ├─ 新建案件
   ├─ 案件类型、案件名
   └─ 返回整理信息
└─ Section: 案件信息
   ├─ 案件类型
   └─ 案件名
└─ Section: 关联资料草稿（可选）
   ├─ 人物关联摘要
   │  ├─ 案件草稿人物行：姓名 / 角色 chips / 从草稿移除
   │  └─ [选择已有人物] [快速创建人物]
   ├─ 主要物件摘要
   │  ├─ 案件草稿主要物件行：名称 / 地址摘要 / 主要物件 badge / 从草稿移除
   │  └─ [选择已有物件] [快速创建物件]
   └─ 辅助说明：案件创建前只是草稿，尚未正式关联；不复制或改变主资料可见范围
└─ Sticky/底部操作
   ├─ 取消
   └─ 创建案件
```

### 4.2 已有案件（Object Page）

```text
Shell / Breadcrumb: 信息整理 / 案件 / {案件名}
└─ Dynamic Page Header
   ├─ 案件名 + 案件类型 + 可见范围 badge
   ├─ [进入案件整理]（当前案件负责人且有可写能力）
   └─ 其他既有案件操作（本阶段不改生命周期）
└─ Section: 关联资料
   ├─ 人物关联（N）
   │  ├─ 人物行：姓名 / 角色 chips / 主资料状态 / 编辑角色 / 更多
   │  └─ [增加人物]
   ├─ 主要物件（0..1）
   │  ├─ 物件行：名称 / 地址摘要 / 主要 badge / 更换 / 解除
   │  └─ [设置主要物件] 或 [更换主要物件]
   ├─ MessageStrip：解除关联只移除本案件关系，不删除人物或物件主资料
   └─ MessageStrip（条件提示）：缺少主要申请人或主要物件时，保证公司申请书暂不可生成
└─ Section: 案件字段（复用现有 CaseOverview）
└─ Section: 输出/既有链路（本阶段只保持原行为）
```

“案件整理”不是新页面产品名，建议先作为详情页内的 `关联资料` 章节，后续若信息量证明必要再抽成独立工作区。

快速创建只定义入口位置、草稿回填和反馈时序，不重新定义人物或物件的字段、必填项、校验、权限或保存合同。实现时必须调用现有人物/物件创建合同；本设计包不批准第二套“最小字段”规则。

## 5. 交互原则

- **先选择，再确认角色。** 选择人物后保持抽屉打开，进入角色选择状态；至少一个固定角色后才能“加入本次草稿”。
- **新建案件只写草稿。** 选择已有资料或快速创建后，摘要行显示“已加入本次案件草稿”；在点击“创建案件”前不使用暗示正式关系已写入的反馈。点击后才一次性提交案件和全部关联，任一失败均不产生部分关联。
- **已有案件详情使用两阶段写入。** 快速创建先保存主资料，再写入案件关联；两步结果必须分开反馈。关联失败时保留主资料并提供重试，不自动删除。
- **选择已有物件即成为草稿中的主要物件。** V1 没有次要物件；若草稿已有主要物件，改为“更换”确认，不允许静默覆盖。已有案件详情允许更换或解除，解除后案件可暂缺主要物件。
- **不把不可选资料当成错误。** 只有当前用户拥有可写能力的资料进入候选；他人仅有公司成员可见／只读、pending、跨主体、suspended、removed 资料不进入候选。空状态解释为“没有可建立关联的资料”，不显示真实总数。
- **重复选择是可恢复状态。** 新建案件草稿中已选人物显示“已在本次草稿”；已有案件中已关联人物显示“已关联”，进入“编辑角色”而不是再次创建关系。
- **最后一个人物角色必须解除关联。** 已有案件中取消最后一个角色先打开“解除关联”确认；新建案件草稿只移除待保存项，并明确主资料不受影响。
- **主要申请人最多一个。** 同一人物可以拥有多个角色，但“主要申请人”角色在同一案件最多一个；没有主要申请人不阻止案件创建，只阻止相关保证公司申请书生成。
- **撤销关系必须可逆地确认。** 弹窗明确“不会删除主资料”，主按钮使用“解除关联”，危险删除词只用于真正删除主资料的未来功能。

## 6. Layout System 组件映射

| 设计区域 | 现有组件/规则 | 使用方式 |
|---|---|---|
| 页面外壳 | Shell、Dynamic Page Header | 保留侧栏、顶部工作区、面包屑和页面标题层级 |
| 创建表单 | `ResponsiveFormLayout`、`ResponsiveFormRow`、`ResponsiveFormField` | 案件信息与关联摘要使用两列；关联抽屉打开时使用 `editorOpen` 右侧编辑槽 |
| 抽屉/编辑层 | `ResponsiveFormEditorSlot`、`editorPanel`、移动端全屏层 | 桌面右侧抽屉；窄屏全屏层；打开时焦点锁定，关闭后恢复到触发按钮 |
| 章节 | `SectionHeader`、`Surface` | Object Page 的“关联资料”章节与子区块统一使用 |
| 状态 | `StatusBadge`、`MessageStrip`、`IssueField` | 只使用“公司成员可见／只读”、草稿、失败等产品状态，不暴露内部能力名 |
| 控件 | `Button`、`IconButton`、`TextInput`、`SelectInput` | 操作层级遵循页面级/章节级/行级，避免同一动作重复出现 |
| 现有列表 | Organize Center List Report | 保留关键词、生命周期过滤、结果数和分页；只增加进入案件关联章节的入口 |

不使用新的颜色系统、卡片圆角、阴影或图标语言；沿用 `src/components/ui-foundation/` 与 `src/app/globals.css` 的 token。

## 7. 多语言与文案原则

本阶段先锁定中文语义，日文/韩文由现有 locale 词典同步，不在页面中写死一种语言：

- 草稿已选：`已加入本次案件草稿`
- 已有正式关联：`已关联`
- 主物件：`主要物件`
- 只读：`公司成员可见／只读`
- 无权候选：`没有可建立关联的资料`
- 解除确认：`解除关联不会删除人物或物件主资料`
- 新建案件页快速创建成功：`主资料已创建，并已加入本次案件草稿；创建案件后正式关联。`
- 已有案件页快速创建成功：分别显示 `主资料已创建` 与 `案件关联操作已完成`
- 新建案件创建失败：`案件未创建，关联也未保存。请检查后重试。`
- 已有案件关联失败：`主资料已创建，但案件关联未保存。主资料没有被删除，请重试。`

任何错误只说明下一步可行动作，不暴露隐藏对象名称、数量、ID 或权限内部字段。

## 8. 焦点、键盘与固定底栏验收合同

### 桌面抽屉

- 打开抽屉后焦点进入抽屉标题或搜索框；Tab/Shift+Tab 只能在抽屉内循环，Esc 关闭并恢复到触发按钮。
- 结果行、角色选择、取消、确认和关闭按钮均可用 Tab 到达；Enter 执行当前聚焦动作，不能绕过角色校验或更换确认。
- 抽屉内容区独立滚动，底部操作栏固定在抽屉内部；最后一行和错误提示必须能滚动到固定栏上方，不被遮挡。
- 抽屉打开时页面底部“创建案件”仍保持可见但不可误触；用户必须先关闭抽屉才能提交案件草稿。

### 窄屏全屏层

- 全屏层打开后锁定背景焦点和背景滚动；焦点进入标题/搜索框，Tab/Shift+Tab 不离开全屏层，Esc 返回原触发按钮。
- 全屏层结构固定为标题区、可滚动内容区、底部固定操作栏；内容区保留足够底部 padding，最后一个结果、角色错误和确认说明不被底栏遮挡。
- 全屏层内不再嵌套第二个 modal；更换物件或解除关联的确认在同一层内完成，并保持清晰的返回/取消路径。
- 关闭、取消、保存失败都恢复原页面滚动位置和触发按钮焦点；失败不清空搜索、已选资料、角色或案件草稿。

上述项目是设计验收项，不代表本轮已经取得真实 `/cases/new` 运行证据；真实截图和键盘回归留到首次 Staging 实现验收。

# 首页工作视图验收标准 2026-06-27

## 目标

本文档定义首页和资料索引从“分类筛选”升级为“工作视图”的验收标准。

本轮目标不是增加更多筛选项，而是让用户在资料数量增加到上百条时，仍然能快速回答：

1. 我现在应该处理哪一批工作？
2. 这些工作为什么进入这个视图？
3. 它们属于哪个案件、物件、客户或未归属资料包？
4. 我下一步应该做什么？

## 发布准入

本轮可以推进实现的前提：

- 所有 P0 条目必须有明确设计和实现路径。
- P1 条目不能与 P0 方向冲突。
- 不得把首页变成大量特征筛选项堆叠的高级搜索页。

## 核心原则

### 1. 视图优先，不是筛选项优先

默认入口应是少量高价值业务视图，而不是让用户面对完整筛选器。

推荐默认视图：

- `待处理`
- `待归属`
- `可输出`
- `资料异常`
- `近期变动`
- `全部`

`案件 / 客户/关系人 / 物件 / 导入资料` 应作为第二层类型筛选，而不是第一层主入口。

### 2. 特征可多，但不能全部露出

确定性特征可以很多，但产品表层只暴露当前视图中有用的少量筛选。

示例：

- `资料异常` 视图中可以露出：缺文件、字段冲突、未归属、输出不可用。
- `近期变动` 视图中可以露出：最近导入、近期租约、近期输出、近期更新。
- `可输出` 视图中可以露出：模板类型、确认状态、负责人。

通过测试：用户不会在默认首页看到一长串业务特征标签。

### 3. 所有视图必须可解释

任何对象进入某个工作视图，都必须能说明原因。

示例：

```text
资料异常
原因：已关联资料中仍有未整理内容
下一步：继续整理
```

可解释信息至少包含：

- 视图命中原因
- 影响的对象
- 推荐动作

如果原因来自导入资料或 AI 建议，必须能在下一屏看到来源或证据。

### 4. 模型辅助入口，不负责最终事实

模型可以用于：

- 把自然语言搜索转成筛选条件。
- 从文件中建议候选特征。
- 解释对象为什么进入某个视图。
- 推荐保存视图名称。

模型不能直接决定最终事实。最终筛选结果必须基于：

- 已确认字段
- 系统规则
- 用户确认后的标签
- 可追溯的历史事件

## P0 验收项

### 1. 工作视图替代类型主筛选

- 资料索引顶部第一层必须是工作视图，而不是对象类型。
- 至少包含：`待处理`、`待归属`、`可输出`、`资料异常`、`近期变动`、`全部`。
- 当前选中视图必须明显可见。
- 列表标题必须显示当前视图名称和结果数量。
- 类型筛选仍然可用，但应放在第二层。

通过测试：用户会先按工作状态进入，而不是先想“我要找案件还是文件”。

### 2. 工作视图定义必须稳定

每个视图必须有确定性定义，不能只靠文案。

最低定义：

- `待处理`：状态不是已整理的对象。
- `待归属`：尚未确认归属的导入资料。
- `可输出`：案件已整理，且有输出准备路径。
- `资料异常`：存在未整理资料、缺失关系、输出不可用或字段冲突。
- `近期变动`：最近导入、更新、生成或确认的对象。
- `全部`：所有对象。

通过测试：同一份数据在刷新后仍然进入同一个视图。

### 3. 视图命中原因必须可见

- 列表行或对象包必须显示进入当前视图的原因。
- 右侧行动面板必须显示更完整的原因。
- 原因文案必须面向业务动作，不使用内部字段名。

通过测试：用户能回答“为什么这条在资料异常里”。

### 4. 结果必须支持对象包表达

当结果属于案件时，应优先按案件包表达，而不是把文件、客户、物件全部平铺成孤立记录。

案件包至少展示：

- 案件标题
- 客户/关系人状态
- 物件状态
- 关联资料状态
- 输出状态
- 当前卡点
- 主操作

未归属资料可以单独成组。

通过测试：上百条资料时，用户看到的是业务对象和卡点，而不是文件堆。

### 5. 搜索和筛选必须保留上下文

- 搜索后仍然保留当前工作视图。
- 类型筛选后仍然保留当前工作视图。
- 清除筛选时不能误清用户仍然需要的搜索词，除非按钮文案明确说明。
- URL 参数应能表达当前视图、类型、搜索词和选中对象。

通过测试：用户可以分享或刷新当前工作视图而不丢状态。

## P1 验收项

### 6. 上下文筛选

- 第二层筛选根据当前工作视图动态显示。
- 当前视图无关的筛选项不默认展示。
- 筛选项数量应保持轻量，默认不超过 6 个。

通过测试：`资料异常` 里看到异常相关筛选，`近期变动` 里看到时间和变动类型相关筛选。

### 7. 保存视图

- 系统内置视图必须固定存在。
- 用户未来可保存自己的常用视图。
- 保存视图至少包含：视图名称、基础视图、搜索词、类型筛选、特征筛选。

本轮可以只预留结构，不一定实现完整保存功能。

### 8. 自然语言筛选入口

- 搜索框可以接受普通关键词。
- 未来可以把自然语言解析成筛选 chip。
- 解析结果必须可见、可编辑、可移除。

示例：

```text
输入：港区 出租不到6个月 缺保证人
解析：区域 = 港区；租约开始日 < 6个月；缺保证人资料
```

本轮不要求完整模型能力，但 UI 不应阻碍未来接入。

### 9. 批量处理入口

当列表中出现多条待归属或待整理资料时，应预留批量处理路径。

典型动作：

- 批量归属到同一案件
- 批量标记暂缓
- 批量打开整理

通过测试：面对多份待归属资料时，用户不会被迫逐条重复打开。

### 10. 最近上下文

首页可以显示“刚刚处理过”或“继续上次工作”，但不能抢过当前工作视图。

内容可来自：

- 最近打开的案件
- 最近整理的资料
- 最近输出的文件

通过测试：用户可以快速回到上一项工作，但默认仍然看到当前待处理队列。

## P2 验收项

### 11. 特征证据

业务特征应支持证据展示。

示例：

```text
出租不到6个月
依据：租约开始日 2026/03/01
来源：租赁申请書.xlsx
```

### 12. 视图质量反馈

用户应能反馈某个对象“不应该出现在这个视图”或“这个标签不准确”。

这类反馈未来可以进入 AI correction learning 或规则修正流程。

### 13. 性能和分页

当对象数量超过 100 时：

- 首屏不应加载所有详情。
- 列表应支持分页、虚拟滚动或服务端分页。
- 搜索和筛选应有明确加载状态。

## 本轮不做

- 不一次性穷举所有房产业务特征。
- 不把模型输出直接当成已确认事实。
- 不把首页改成复杂 BI 或 CRM 报表。
- 不在默认首页展示超过 6 个主要工作视图。
- 不为了高级筛选牺牲“下一步处理”的主线。

## 复核清单

实现后必须复核：

- 默认进入 `待处理` 或等价工作视图。
- 切换到 `待归属` 后只看到未归属资料或对应对象包。
- 切换到 `资料异常` 后每条结果都有原因。
- 搜索后仍保留当前视图。
- 类型筛选作为第二层存在。
- 390px 移动端可以使用工作视图切换。
- 中文界面不硬翻译日本专名。

必须通过的工程检查：

- `npm run lint -- --quiet`
- `npx tsc --noEmit --pretty false`
- `npm run test:ja-terms`
- `npm run test:case-field-catalog`
